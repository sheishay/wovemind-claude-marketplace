# Why the orders table keeps growing even though we delete old rows

The short version is that it is MVCC plus autovacuum thresholds plus the long-running reporting transaction, but the full explanation needs a few pieces in place, so bear with me.

PostgreSQL uses multiversion concurrency control (MVCC), which means an `UPDATE` never changes a row in place: it writes a new version of the row (a new tuple) and marks the old one as expired by setting its `xmax` to the ID of the transaction that replaced it, while a `DELETE` just sets `xmax` without writing anything new. The old tuple stays physically in the table's pages, because some other transaction that started earlier might still need to see it, and it becomes a "dead tuple" only once no running transaction could possibly see it anymore, that is, once every transaction still running started after the deleting or updating transaction committed. Dead tuples take up space until `VACUUM` processes the table, finds them, and marks their space as reusable in the free space map. Note that ordinary `VACUUM` does not give space back to the operating system (except for completely empty pages at the very end of the file); it only makes the space reusable for new rows in the same table. `VACUUM FULL` does give space back, by rewriting the whole table, but it takes an `ACCESS EXCLUSIVE` lock for the whole duration, which blocks all reads and writes, so on a 40-million-row table during business hours it is not an option. `pg_repack` can do the same rewrite with only brief locks, which is what you would use if you need to reclaim the space that is already bloated.

Autovacuum decides when to vacuum a table using a threshold: it vacuums when the number of dead tuples exceeds `autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * number_of_rows`. The defaults are a threshold of 50 and a scale factor of 0.2, which means 20 percent of the table. For the orders table, with about 40 million rows, that is 50 + 0.2 * 40,000,000, so roughly 8 million dead tuples have to pile up before autovacuum even starts. The nightly job deletes about 300,000 old orders, and the status updates during the day create another 500,000 or so dead tuples, so it takes about ten days to reach the threshold, and by then the table has a lot of dead space that new inserts may or may not reuse depending on where it is.

But that alone would just make vacuum late, not make the table grow forever. What makes it grow forever is the reporting job. The finance export opens a transaction at 06:00 and keeps it open for about five hours while it pages through results with a cursor. While any transaction is open, VACUUM cannot remove any tuple that became dead after that transaction started, because in principle that transaction might still need to see it (this is the "oldest xmin" horizon; you can see it in `pg_stat_activity.backend_xmin`). So for five hours every day, nothing that dies can be cleaned up anywhere in the database, not only in the orders table, and if autovacuum happens to run during that window it does the work of scanning the table but removes far fewer tuples than it should. You can confirm this: `pg_stat_user_tables.n_dead_tup` for orders is currently about 11 million, and the autovacuum log lines show "tuples: 0 removed, 11204331 remain, 10987112 are dead but not yet removable" on the runs that overlapped the export.

There is a second, slower risk tied to the same mechanism. Transaction IDs are 32-bit counters, so after about 2 billion transactions they wrap around, and PostgreSQL must "freeze" old tuples before that happens, which is another thing VACUUM does. If freezing is blocked for long enough, PostgreSQL will eventually force an aggressive anti-wraparound vacuum, and in the extreme case it stops accepting writes to protect the data. We are nowhere near that (`age(datfrozenxid)` is about 310 million, against the default `autovacuum_freeze_max_age` of 200 million that triggers aggressive vacuums, so those are already running, which partly explains the extra I/O in the mornings), but the long transaction makes it worse.

What to do, in order of impact:

1. Stop the reporting transaction from staying open for five hours. Either run the export against the read replica (with `hot_standby_feedback` off, so the replica's queries do not hold back vacuum on the primary; the cost is that a very long query on the replica can be cancelled with a conflict error, so the export should retry), or change it to fetch in batches by primary key with a fresh short transaction per batch.
2. Lower the scale factor for the orders table only: `ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_threshold = 10000);`. That brings the trigger down from about 8 million dead tuples to about 410,000, so autovacuum runs roughly daily instead of every ten days. Do not change it globally, because small tables are fine with the default.
3. Optionally raise `autovacuum_vacuum_cost_limit` from the default of 200 (in effect) to something like 1000 for this table, so each vacuum finishes faster. Watch disk I/O when you do.
4. Once the first three are in place, run `pg_repack` on the orders table once, during a quiet period, to reclaim the space that is already bloated, which I estimate at about 35 percent of the table's 62 GB on disk.

As an aside, partitioning the orders table by month would make the nightly delete a simple `DROP` of an old partition, with no dead tuples at all, but that is a much bigger change and not needed to fix this.
